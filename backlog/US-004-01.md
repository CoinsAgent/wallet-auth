# US-004-01 — Authorize remote and headless CLI applications using Device Authorization

## User story

As a wallet owner operating a CLI in a remote or headless environment, I want to authorize the CLI through SIWE and explicit consent on a separate browser-enabled device, so that it can obtain and automatically renew OAuth access tokens without requiring a local browser, SSH port forwarding or a hosted callback relay.

## Story map context

- Journey/activity: [Application owner](STORY_MAP.md#application-owner) — authorize a CLI, obtain OAuth credentials, renew authorization and revoke individual grants.
- Proposed release contribution: a remote Linux CLI obtains and maintains human-delegated authorization through a separate browser, with the same identity, permission and lifecycle boundaries as [US-004](US-004.md).
- Dependency: US-004 supplies the deployment-owned public CLI identity, SIWE consent, resource-bound opaque management tokens, independent grants, refresh rotation and revocation. This story adds an authorization entry point only; it does not change US-004 or introduce new business operations.
- Governing documents: [Vision](../docs/VISION.md), [Product Contract](../docs/PRODUCT_CONTRACT.md), [UI Design Contract](../docs/UI_DESIGN_CONTRACT.md), [Process](../docs/PROCESS.md).

## Consolidated design

Reuse the existing public WalletGate CLI client for Authorization Code + PKCE and RFC 8628 Device Authorization. Share authorization policy, not individual grants or credentials. A public client ID identifies the application, not a verified executable or physical device.

Proposed CLI command: `walletgate login --device`. Preserve existing login and explicit flow selection. The CLI obtains device authorization information, displays verification URL, user code and QR, and polls the OAuth token endpoint. On a separate browser-enabled device the human completes SIWE when necessary before any user-code lookup, confirms the code, reviews the authorization and explicitly approves or denies. Continued-access consent is required for successful device login; declining it issues no credentials. Successful redemption yields OAuth credentials rather than browser sessions. Automatic renewal continues within the existing delegated lifetime; expiration or revocation requires new human authorization.

Reuse native Better Auth OAuth Device Authorization (documented as oauthDeviceAuthorization with oauthProvider), subject to pinned-version compatibility verification. Better Auth owns server protocol mechanics; WalletGate owns SIWE provenance, consent, eligibility, grant binding, lifecycle and CLI UX. No custom RFC 8628 implementation or upstream fork is authorized.

| Policy | Selected behavior |
| --- | --- |
| Public client | Existing approved deployment-owned CLI identity |
| Pending device authorization | Fixed 300 seconds from issuance; no extension |
| Initial polling interval | 5 seconds; obey server interval and slow_down |
| Access token | Opaque, resource-bound, maximum 900 seconds |
| Refresh token | Explicit offline consent required for successful device login; strict rotation |
| User-code lookup | SIWE-proven session required; at most five incorrect submissions per session in a fixed five-minute window, shared across codes and tabs; no new persistent IP tracking |
| Inactivity deadline | 7 days under existing US-004 activity policy |
| Absolute authorization deadline | 30 days from original consent |
| Browser session | Reuse only valid SIWE-proven sessions; issued grants independent |
| Revocation | Individual authorization; preserve unrelated grants |

## Acceptance criteria

AC-01–AC-12 were selected by the human in Grill Round 10 for DRAFT story shaping. AC-13 records the subsequent Q12–Q14 fresh-storage/reset decisions. Q15–Q16 further specify AC-04/05/06/08. None is READY approval or evidence of implementation.

- AC-01: Native RFC 8628 integration — Use supported Better Auth OAuth Device Authorization and standard grant semantics. Issue OAuth access tokens through the OAuth token endpoint, not standalone Better Auth session credentials. Avoid duplicating native protocol mechanics or modifying upstream source. Verify endpoint interoperability and discovery metadata where applicable.
- AC-02: Public client eligibility — Reuse the existing system public CLI client ID for both grants, without a distributed secret or new system client. Only explicitly eligible clients initiate/redeem requests; bind requests to their initiating client, intended management resource and permitted scopes. Preserve existing PKCE, redirect and third-party restrictions. Public client ID is not executable authentication.
- AC-03: Headless initiation — A remote Linux CLI explicitly initiates Device Authorization without a browser, callback listener, forwarding or relay. Display trusted verification URL, user code, expiry, status and scannable terminal QR encoding the server-provided verification_uri_complete when available, otherwise verification URI with manual code entry. Retain manual URL/code fallback. Never display or log confidential device code, access or refresh tokens. Scanning alone does not authorize.
- AC-04: SIWE authentication — A human completes the flow on a separate browser. Reuse only unexpired server-verified SIWE-proven sessions; absent, expired or non-SIWE authentication requires valid SIWE. Wallet connection alone is insufficient. Require a valid SIWE-proven session before any user-code lookup, including a code supplied by the complete verification URL; retain the pending link through authentication without revealing request details early. Show authenticated wallet and allow switching/re-review; changed wallet/session cannot silently approve an earlier reviewed request.
- AC-05: Explicit consent — Every new grant requires deliberate approval after review of application, wallet, matching user code, requested permissions/scopes, target clients where relevant, offline access and lifetime. Bind consent to exact request, verified session and approved selection. Reject automatic consent reuse, altered requests, permission expansion and direct native endpoint bypass. Preserve existing owner/target boundaries and UI design requirements, including mobile and accessible interaction. Explain before approval that device login requires continued-access consent; declining it ends this login without issuing access or refresh credentials. No new client-management functionality.
- AC-06: Device code lifecycle — Use cryptographically secure device codes, sufficiently unpredictable human-readable codes and server-side guessing limits. Allow at most five incorrect user-code submissions per authenticated session in a fixed five-minute window shared across codes and tabs; further submissions are blocked for the remainder of that window, with an understandable retry message. Do not add persistent IP tracking. Enforce five-minute original deadline for both approval and redemption. Pending requests issue no tokens; denied, invalid, expired, consumed and wrong-client codes cannot issue tokens. Successful redemption consumes the code once; lost response requires new authorization. SIWE and approval never extend expiry. CLI cancellation stops polling; absent supported server cancellation, pending request expires naturally. Do not claim immediate server cancellation without confirmation.
- AC-07: Polling — Use urn:ietf:params:oauth:grant-type:device_code at the OAuth token endpoint. Obey server interval (initially five seconds), continue on authorization_pending, add five seconds on each slow_down for subsequent requests, reduce frequency after connection timeouts, stop on access_denied, expired_token, other OAuth errors or success. Communicate outcomes and respect original deadline. Use trusted HTTPS endpoints and protect credentials.
- AC-08: Token issuance — After approval issue opaque management access tokens with maximum 15-minute lifetime, correct issuer, wallet principal, calling client, management resource, approved scopes and independent grant identity. Device login requires explicit offline consent; without it issue neither access nor refresh credentials and report login declined. Do not offer an access-only successful device login in this slice. Preserve protected CLI storage; never transfer browser cookies or session tokens. Tokens cannot outlive applicable grant deadlines or bypass existing resource/permission checks.
- AC-09: Renewal — Automatically renew via refresh_token grant while authorized; preserve strict rotation without replay grace, owner/client/resource/permission binding and protected persistence across restart. Consumed refresh credential replay invalidates only its grant; lost rotation response follows existing reauthorization recovery. Refresh cannot expand permissions or reset absolute lifetime. Browser logout/session expiry does not terminate independently issued valid grants. Inherit same-profile replacement across PKCE and device login: require the same issuer and wallet; successful replacement revokes only that profile’s prior grant; denial, cancellation, expiry or failure before success preserves it. Separate profiles retain independent grants.
- AC-10: Expiry and human reauthorization — Enforce seven-day inactivity and 30-day absolute lifetime from original consent, whichever occurs first. Successful refresh or authorized activity as defined by US-004 resets inactivity; failed requests, page visits and inspection do not. At either deadline access and renewal are rejected and new human authorization is required. Access token expiry alone does not require human action when valid refresh authorization exists.
- AC-11: Revocation — Reuse existing owner authorization listing and individual revocation. Show device grants with existing labels, unique IDs, timestamps and permissions; labels are not verified device identities. Owner revocation or CLI logout invalidates the selected grant's access and refresh credentials after effective revocation without affecting other device or PKCE grants. Reject foreign-owner revocation. Browser logout is distinct. If server revocation cannot be confirmed, report incomplete logout and retain protected credentials for retry per US-004. Preserve existing downstream grant-invalidation rules without adding operations.
- AC-12: Regression protection — Existing local PKCE and SSH-forwarded login, SIWE-only authentication, canonical wallet OIDC subject, third-party OAuth/OIDC, owner-scoped registration/management, refresh and revocation continue working. Exercise existing business operations solely as authorization-boundary regression tests, not new functionality.
- AC-13: Fresh storage and explicit local reset — Support newly initialized databases with required device storage and system CLI eligibility. A separate explicit local development/test reset command discards existing application data and initializes the current schema, invalidating prior sessions, registered clients and grants. Normal startup refuses incompatible storage without changing it. No conversion/migration or deployed/shared database reset is included. Verify with disposable databases and negative cases for unsafe reset invocation.

## End-to-end verification expectations

- Positive: remote Linux login without local browser/forwarding; scan real QR on separate device and verify manual fallback; fresh SIWE and valid-session reuse; explicit consent; OAuth redemption; protected persistence and automatic renewal; independent revocation.
- Negative: no credentials after declining continued access; unauthenticated user-code lookup and code-guessing attempts across codes/tabs; no tokens before approval; denied/expired/replayed/wrong-client codes; non-SIWE authentication; altered consent and direct endpoint bypass; unauthorized resource/scope/target; refresh replay; revoked credentials; cross-wallet revocation.
- Boundaries: before/at/after 300-second device expiry, 900-second access maximum, seven-day inactivity and 30-day absolute deadline; approval just before expiry with redemption after expiry; slow_down and timeout backoff; local cancellation and response-loss recovery; browser logout independence and grant isolation; fifth incorrect user-code attempt versus subsequent attempts and the exact fixed-window reset boundary; successful cross-flow profile replacement versus failure preserving previous credentials; explicit reset of disposable local storage and unchanged incompatible storage on ordinary startup.
- Regression: run existing US-004 and third-party OIDC tests plus focused protocol/UI tests and full repository verification before QA_PASSED. Record actual commands, results and limitations in delivery evidence. Shaping did not execute these checks; actual delivery commands and results belong in work/US-004-01/evidence.md.

- New business operations or changes to existing IAT, ownership, target permissions and quotas.
- Physical device registry, fingerprinting, trusted-device identity, hosted callback relay and automatic environment-based flow selection.
- Custom RFC 8628 implementation or Better Auth fork without separate human approval.
- Existing-data conversion/migration, deployed/shared database resets, production deployment, external agent installation or registry publication. Local development/test reset through a separate explicit command is included; normal startup never deletes data.
